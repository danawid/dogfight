# Lab 01: відповіді на питання Reflection

## 1. Середовище виконання і `setTimeout(f, 0); Promise.resolve().then(g);`

```txt
 ┌──────────── рушій (V8) ────────────┐      ┌──── браузер (Web APIs) ────┐
 │  Heap (об'єкти)   Call Stack        │ ───► │ таймери, DOM-події, fetch  │
 └─────────────────────────────────────┘      └─────────────┬──────────────┘
          ▲                                                 │
          │   event loop: стек порожній → беремо наступне    ▼
 ┌──────── Microtask queue ────────┐   ┌────────── Task queue ──────────┐
 │ .then, await, queueMicrotask    │   │ setTimeout, події, повідомлення│
 └─────────────────────────────────┘   └────────────────────────────────┘
          Render steps: rAF → style → layout → paint
```

1. `setTimeout(f, 0)` віддає `f` таймеру браузера; коли час вийшов, `f` потрапляє в
   **task queue**.
2. `Promise.resolve().then(g)`: проміс уже виконаний, тому `g` одразу стає в
   **microtask queue**.
3. Скрипт завершився, стек порожній. Спершу мікрозадачі виконуються **повністю**:
   `g`. Далі браузер може намалювати кадр. Потім наступна задача: `f`.

Результат: `g`, потім `f`.

## 2. Чому синхронний цикл на 100 мс заморожує всю сторінку

Є один потік. Поки функція на стеку, event loop не може взяти наступну задачу, виконати
мікрозадачі чи зробити рендер: рендер теж відбувається на головному потоці між задачами.
Тому не працюють кліки, таймери, rAF, CSS-анімації, яким потрібен layout/paint (анімації
`transform`/`opacity` на композиторі й прокрутка інколи продовжуються, бо їх веде окремий
потік).

JavaScript не може перервати сам себе: немає переривань і витіснення. Можна лише **не
блокувати**: поділити роботу на шматки (`setTimeout`, `scheduler.yield()`) або винести її
у **Web Worker**. В експерименті 1 це видно: steps/s лишається 60, бо акумулятор
надолужує кроки після паузи, але картинка на 100 мс завмирає.

## 3. Задачі та мікрозадачі

- **Задача:** одна за ітерацію циклу; між задачами браузер може рендерити.
- **Мікрозадачі:** після кожної задачі (і після кожного колбеку, коли стек порожній)
  черга виконується **до кінця**, включно з мікрозадачами, доданими під час виконання.

Ланцюжок мікрозадач ніколи не дає черзі спорожніти, тому рендер не настає. Ланцюжок
`setTimeout` кожного разу створює нову задачу, а між задачами браузер встигає
намалювати кадр.

## 4. Де виконується `requestAnimationFrame`

rAF не є ні задачею, ні мікрозадачею. Це **крок рендеру**: після задачі та її мікрозадач,
коли браузер вирішив малювати кадр (за vsync), він викликає всі rAF-колбеки, потім
style → layout → paint.

Чому rAF кращий за `setInterval(fn, 16)`:

1. Синхронізований з оновленням екрана: немає пропущених і подвоєних кадрів. 16 мс не
   дорівнює 16,67 мс, тому інтервал «пливе».
2. Сам підлаштовується під 60/120/144 Гц.
3. Зупиняється у фоновій вкладці: не витрачає батарею і CPU.
4. Дає точну мітку часу кадру; всі колбеки одного кадру виконуються разом.

## 5. Цикл з акумулятором

```js
accumulator += Math.min(delta, 0.25);
while (accumulator >= STEP) {
  simulate(STEP);
  accumulator -= STEP;
}
render(accumulator / STEP);
```

Реальний час накопичується в акумуляторі й «витрачається» шматками рівно по `STEP`.
Залишок переходить у наступний кадр.

- **Clamp (0,25 с)**: після зависання (фонова вкладка, breakpoint, GC) без обмеження
  довелося б виконати сотні кроків за раз. Якщо ці кроки довші за реальний час, буде
  «спіраль смерті». З обмеженням гра просто трохи сповільнюється, а не телепортує
  корабель крізь стіни.
- **alpha** = частка кроку, яка «не встигла» виконатись (0…1). Рендер малює стан між
  попереднім і поточним: `lerp(prev, curr, alpha)`. Тому рух плавний на 120 Гц, хоча
  симуляція йде 60 разів/с.

## 6. Навіщо детермінізм і до чого тут мультиплеєр

Детермінізм означає: ті самі вхідні дані дають той самий результат. В експерименті 3
з фіксованим кроком позиція після 300 кроків однакова і з тротлінгом, і без. Зі змінним
кроком позиції розходяться.

У мультиплеєрі (Lab 5) клієнт і сервер симулюють ту саму гру. Клієнт передбачає свій
рух, а коли приходить стан із сервера, перевиконує свої введення. Якщо симуляція
залежить від частоти кадрів, клієнт на 144 Гц і сервер отримають різні траєкторії та
різні зіткнення: постійні «ривки» й розсинхрон.

## 7. Що захоплює замикання

**Змінні (прив'язки), а не значення.**

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 3 3 3
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 0 1 2
```

- `var` створює одну змінну на всю функцію. Усі три колбеки бачать ту саму `i`, а
  виконуються вони після циклу, коли `i === 3`.
- `let` у циклі `for` створює **нову прив'язку на кожній ітерації**, тож кожне
  замикання бачить свою `i`.

У проєкті `createInput()` тримає `down` і `pressed` у замиканні: ззовні їх не змінити,
доступ лише через `isDown`/`justPressed`.

## 8. Що змінює `type="module"`

1. Кожен файл має власну область видимості: верхньорівневі `const` не стають глобальними.
2. Завжди strict mode.
3. Працюють `import`/`export`; імпорти є живими прив'язками, а не копіями.
4. Скрипт відкладений (як `defer`): виконується після розбору HTML.
5. Працює top-level `await`.
6. `this` на верхньому рівні дорівнює `undefined`, а не `window`.
7. Модуль виконується один раз, хоч скільки файлів його імпортує.
8. Завантажується з CORS: з `file://` не працює, потрібен сервер (Vite).

## Можливі додаткові питання

- **Чому `justPressed` очищується після кроку, а не після кадру?** На 120 Гц частина
  кадрів не має жодного кроку симуляції: натискання загубилось би. На повільному
  кадрі з двома кроками натискання спрацювало б двічі.
- **Чому арена фіксованого розміру 1600×900, а не розміром вікна?** Світ має бути
  однаковим для всіх гравців. Вікно лише масштабує картинку.
- **Навіщо `lerpWrapped`?** Коли корабель перелітає край (x: 1599 → 1), звичайний lerp
  на один кадр намалював би його посеред арени.
- **Навіщо `lerpAngle`?** Між 179° і −179° різниця 2°, а не 358°. Без цього корабель на
  один кадр робив би повний оберт.
